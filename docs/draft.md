# agent-InferTriage：Agent 性能分诊器项目草案

状态：独立项目需求草案，配套实施计划见 plan.md，尚未进入实现。

项目名称：agent-InferTriage。本文中的产品名与仓库名使用此拼写；命令行暂用小写 agent-infertriage。不假设 PyPI 或域名可用。

本版已纳入的明确需求：五个层面的阶段及多轮耗时、token 消耗、缓存利用、成本；离线诊断与 Agent 日志分析两条调用路径；每次诊断自身的 token 与时间开销。两条路径均属于首版必需能力。

## 1. 本草案的用途与项目归属

我们已经完成功能方向讨论。这份文件作为独立开发计划的需求输入，不再使用 hmz、humanize1-flow 或其 gen-idea/gen-plan/rlcr 流程。

目标是开发一个独立开源项目。请在 agent-InferTriage 自己的目标仓库内规划和实现；即使该仓库尚无代码，也应将其视为按本草案启动的新项目。开发与运行均不依赖特定 Agent 编排框架。

规划阶段需要决定具体模块、接口、任务顺序和测试方式。可以调整实现细节，但应保留本文的产品目标、证据边界和阶段范围。本文件不是要求一次实现所有远期能力的全量计划。

## 2. 产品要回答的问题

> 下一周的性能优化时间，应该花在 Agent 编排、Prompt、缓存、推理调度，还是 Kernel 上？证据是什么，最多可能改善多少，还需要什么实验来确认？

agent-InferTriage 分析已经发生的 Agent 执行记录、日志和 profile，并在可选接入服务端数据后关联推理服务状态，输出有证据、带条件的优化优先级。用户可以选择确定性的离线分析，也可以选择由诊断 Agent 读取日志、调用分析工具并逐步形成诊断。

端到端任务耗时、逐阶段/逐轮耗时、token 消耗、缓存利用和成本均为必需报告维度。优化排序默认关注端到端任务耗时，也允许用户单独查看 token 与成本机会；各维度不能互相替代。减少 token 不一定降低用户账单，也不一定缩短关键路径。

必须维护两套独立记录：workload 描述被分析的 Agent 任务，diagnosis 描述本次诊断过程自身。日志里已有的模型消耗不能当作诊断新消耗；诊断 Agent 的调用也不能混入原任务。

用户保留系统修改权。产品不自动修改 Prompt、模型、Agent 代码、引擎参数、路由和 Kernel，也不自动重启服务。

GitHub 千星是传播愿景，不是可以保证的产品结果，也不是开发验收指标。首先证明工具能帮助用户作出正确的优化决策。

## 3. 目标用户和首发场景

主要用户是构建多轮 Coding Agent、Research Agent 或数据分析 Agent 的开发者，以及为这些应用维护 vLLM/SGLang 服务的推理工程师。

典型系统包含多轮 LLM 请求、工具调用、子 Agent、持续增长的上下文，以及一个或多个推理服务。典型问题包括：

- Agent 随着轮次增加越来越慢，团队不知道是上下文膨胀还是服务退化。
- 子 Agent 并发扇出后尾延迟恶化，应用和推理团队对排查方向有分歧。
- 开启 Prefix Cache 后收益不明显，需要检查实际复用条件和服务端证据。
- 团队准备优化调度或 Kernel，需要先判断其端到端改善空间。
- 升级 Agent、Prompt 或推理服务后性能回退，需要定位变化发生在哪一层。

首个真实工作负载选择一个可导出结构化 trace 的多轮 Coding/Research Agent 任务，观察上下文增长、工具执行、重复测试和审查轮次。不能预先假设独立 reviewer 的重新读取就是浪费。闭源模型后端不能提供的内部指标应明确缺失。

## 4. 四项核心能力

### 4.1 还原端到端关键路径

把 Agent 任务表示成有明确依赖关系的执行图，区分 LLM、工具、子 Agent、应用处理和等待。数据充分时，进一步细分请求排队、Prefill、Decode 和其他服务端阶段。

报告需要解释哪些步骤决定任务完成时间、哪些步骤存在并行余量，以及还有多少时间未归因。时间轴与关键路径应可相互核对。

父子 span 的包含关系不等于数据依赖，时间上相邻也不证明存在依赖。不能仅凭 parent_id 或时间戳就把不确定关系伪装成精确的关键路径。

### 4.1.1 全阶段与多轮观测矩阵

报告必须始终展示 Agent 编排、Prompt、缓存、推理调度、Kernel 五个层面。LLM 请求、工具、网络、应用处理和未归因时间作为必要的关联活动保留，不能为了凑成五行而丢失时间。

| 层面 | 有证据时需要展示的耗时 | token、缓存与成本的对应关系 |
| --- | --- | --- |
| Agent 编排 | 规划、分发、fork/join 等待、工具/子 Agent 调用、重试与本地处理 | 汇总其关联 LLM 请求用量与成本，明确包含关系；工具/API 费用单列 |
| Prompt | 组装、模板渲染、序列化、tokenization；关联请求的 Prefill 单独链接 | 展示 system/history/tool schema/tool result 等输入构成与逐轮增长；没有内容时标记构成未知 |
| 缓存 | 已观测的查询、命中、加载、写入、传输、驱逐/重算相关活动 | 分开报告 Prompt/KV/工具缓存；命中量、查询量、读写 token、占用和成本各自注明语义 |
| 推理调度 | 入队/出队、排队、准入等待、抢占、调度执行及其他已观测等待 | 引用同一请求的用量、批次和 KV 压力，不再次计为独立 token 消耗 |
| Kernel | 具有来源与关联证据的 kernel 执行、通信及同步活动；支持多次调用 | 展示关联请求/批次的 token 和 GPU 资源成本口径；没有独立 token 计费时标为不适用 |

这些层面不是天然互斥的五个顺序阶段。Prefill 可同时关联 Prompt、缓存和 Kernel；总 token/成本仅在原始请求上记账一次，跨层视图只能引用。累计 kernel device time、GPU 活跃时间与任务 wall time 分别展示，不能直接相加。

每个层面允许在任务中出现多次，必须保留所有轮次和调用明细。至少支持 task → agent/sub-agent → workflow round → stage occurrence → request/attempt → engine iteration/kernel invocation 的关联；层次按实际数据使用，不要求所有来源都有全部字段。该链条是导航与关联视图，不强制为一棵树：共享批次、跨轮缓存和多个请求共用 Kernel 可保留多对多关系，不能复制为独占活动。

用户可以按轮次、阶段实例、Agent、请求或整个任务查看耗时、token、缓存和成本，同时查看总量、分布和变化趋势。工具重试、Agent 轮次、模型 Decode step 和 Kernel 重复调用是不同维度，不得混成一个 round。单阶段内的多轮也必须可展开，不能只保留均值或总和。缓存利用应关联到每次调用或其可获得的采样区间；没有逐轮采样时标记粒度限制，不能用全程均值冒充每轮观测。

耗时至少区分 elapsed/inclusive、可确定的 self/exclusive、累计活动时间和关键路径贡献。缺少足够数据时不输出伪精确的 self time 或关键路径贡献。

五个层面都要有覆盖状态：observed、partial、unknown 或 not_applicable。缺少服务端日志/profile 时不能从客户端请求时间还原真实调度与 Kernel 时间，应显示缺失字段和补采方式。可选的来源适配不意味着可以从首版报告中删除这些维度。

### 4.2 可选的主动鉴别实验

当同一症状有多个可能原因时，提出最小、可解释的下一项实验，说明它区分哪些假设、为何值得执行、需要什么观测，以及何时结果仍不能得出结论。

可能的实验包括相同前缀重复请求、受限并发对照、输入/输出长度对照。第一项实际实验优先选择受预算约束的前缀复用探针。

主动实验是独立能力，默认关闭。分析既有数据不应隐式触发模型请求。实验需显式启用，并事先列出目标 endpoint、请求数、预计输入/输出 token、最大输出长度、超时和停止条件。

有副作用的真实工具不自动重放；工具 mock 只在隔离的实验驱动中使用。主动发送请求会改变缓存与服务负载，报告必须记录这种干预。

### 4.3 识别 Agent 特有的推理浪费候选

重点发现可归属到开发者能够修改的位置的问题，例如上下文持续膨胀、重复文件读取、工具结果反复携带、前缀被动态内容打断，以及无进展的重试循环。

规则首先报告事实和候选机会，而不是武断地判定调用无用。重复工具调用可能是必要的状态刷新；长输入可能是任务所需；重复前缀也可能已被便宜地缓存。

### 4.4 给出有条件的收益上限与投入排序

每条结论都应附带收益信息，或明确说明无法计算的原因。报告区分：

1. 直接观测量：耗时、请求数、token 和已观测缓存量。
2. 条件性理论上限：在明确的图模型和不变条件下，最多能缩短多少任务耗时。
3. 模型估计：只有存在可核验的性能模型时才提供，并列出假设。
4. 实验测得的差异：列出实验条件、样本量、变异和质量约束。

未知收益用 null/unknown 表达，不能记作 0。无法观测 Kernel 时，不能把它排到末尾并声称“不值得优化”。

## 5. 产品差异化与非目标

核心输出是按证据和端到端改善空间组织的工程投入建议。用户应能追溯到具体调用、依赖、指标和计算，而非只得到一段泛化建议。

本项目不扩展为通用自动调参器、长期监控告警平台、Prompt 管理平台、模型路由器、成本账单系统或通用 Agent evaluation 平台。首版不开发 CUPTI/Nsight 采集器，不生成和替换 Kernel，不训练诊断模型。

开发与代码审查按独立实施计划推进。正常使用 agent-InferTriage 不应要求用户安装任何特定 Agent 编排框架或运行多个模型。两条诊断路径共用确定性的计量、关键路径、规则和收益计算模块；Agent 路径可调用模型解释和选择后续日志查询，但所有数值结论必须引用工具结果，不能由 LLM 自行编造。

## 6. 交付阶段与范围

### 阶段 A：v0.1，两条诊断路径与完整计量闭环

必须包含：

- 一个版本化的 JSON/JSONL 输入格式，覆盖执行时间、五层阶段、多轮标识、请求用量、缓存、成本、显式依赖及原始证据引用。
- 数据完整性校验、证据覆盖说明，以及缺失数据时的降级行为。
- 全阶段/逐轮/逐调用的耗时、token、缓存与成本视图；能导入包含服务端阶段与 Kernel 标注的标准证据包。首版不必直接解析所有厂商的原始 profile。
- 对依赖信息完整的记录计算关键路径和条件性收益上限。
- 三类规则：上下文/工具结果增长、重复工具调用/疑似重试循环、前缀复用受损候选。
- 可追溯的 finding，以及按相同目标组织的优化候选清单。
- 终端摘要、机器可读 JSON 和可离线打开的单文件 HTML 报告。
- 无账号、无 API key、无 GPU、无模型请求即可运行的演示数据。
- 一个真实数据导入路径，优先选用 OpenTelemetry 导出的多轮 Agent trace；只使用实际可获得的字段。
- 可独立调用的 offline 和 agent 两种模式：前者只用本地确定性工具，后者完成读取日志、调用分析工具、检查假设、输出诊断的最小有界循环。
- 至少一个实际可配置的模型调用适配器用于 Agent 模式，支持记录响应 usage 和各次请求时间。无凭据的自动测试使用固定响应/mock，不以此冒充已经完成的真实模型接入。
- 两种模式均输出 diagnosis_id、状态、诊断自身总 wall time、模型调用次数、输入/输出/总 token、已知用量覆盖与费用信息；offline 模式新增模型调用为零。

如果真实记录缺少精确 span 时间、token、工具边界或依赖，应如实保留缺失。不能补造数据以满足报告格式。首个适配器选择明确有文档且可验证的 trace 导出格式，并记录字段支持范围。

v0.1 不要求在线代理、实时监控、新开发 GPU profiler 或实际主动探针执行。现有日志/profile 中的阶段数据可离线导入并由两条路径分析。必须保留后续扩展所需的证据和实验建议接口，不能用空实现宣称已能在任意系统自动采齐五层数据。Agent 日志分析是首版必需能力，不能推迟到“以后加入 LLM 解释”。

### 两条路径的执行语义

路径一 offline：用户提供日志/trace/标准证据包 → 本地解析与归一化 → 确定性计量、规则与图分析 → 输出诊断及诊断自身计量。运行时不调用模型、不发起网络请求；本次新增推理 token 为 0，但诊断耗时必须实际测量。分析期间在本地 tokenizer 上处理文本不计为模型调用 token。

路径二 agent：用户显式选择模式并提供模型配置 → 诊断 Agent 读取用户指定的日志/证据 → 按需调用只读解析、检索、计量和关键路径等工具 → 根据证据提出/检查假设 → 输出同样结构的诊断及诊断自身计量。日志可完全来自历史文件，Agent 模式不等于重跑用户 Agent、重新生成原任务结果或进行主动服务探针。

Agent 路径每一轮分析、工具调用、模型调用、重试与最终报告生成都必须留痕并纳入 diagnosis。模型可使用本地推理或用户配置的远程服务；即使本地服务不按 token 收费，实际 token 和耗时仍须记录。诊断 Agent 不得把待分析日志内的指令当成执行指令。

Agent 模式的预算至少包含最大轮数、模型调用数、输入/输出 token 限制、总时长和工具输出截断策略。调用预算在发出下一请求前检查；provider usage 缺失时允许采用标注为估计的本地计数，并以请求、长度和时间上限兜底。默认不启动分析子 Agent；未来支持时其消耗必须归入同一 diagnosis_id。

切换到 agent 仅授权读取选定数据、执行分析工具与调用选定模型。主动探针另有显式开关和独立预算；没有启用时，两条路径都不得发送测试负载到被分析服务。

### 阶段 B：服务端关联与首个主动探针

- 先支持一种已固定版本并经过验证的 vLLM 指标输入/只读采集路径。
- 读取请求队列、KV Cache、preemption、请求延迟等实际可用信号。
- 关联同一采集窗口，标记服务共享、采样粒度和时钟偏差等限制。
- 实现显式启用且有预算的前缀复用探针；客户端耗时改善本身不证明命中后端缓存。
- 输出探针前后的证据变化，并允许“未能区分候选原因”的结果。

阶段 B 可先支持离线保存的引擎样本，不必立即搭建常驻采集服务。阶段 A 完成后再进入阶段 B 的实现；实施计划应先明确阶段 A 的完成边界。

### 后续阶段：基于真实用户需求扩展

SGLang、更多 trace 适配器、多实例调度、版本回退对比、实验选择排序，以及直接解析更多原始 GPU/Kernel profile。首版要求支持标准证据包内的 Kernel 数据；采集器和更多原始格式解析可后续扩展。DeepInfer 作为后续候选适配器，不阻塞首版。

Kernel 结论需要来源明确的 profile 和足够的请求/批次关联。只有整台 GPU 的利用率或全局 kernel 时间，不能直接分配到某个 Agent 任务。

## 7. 数据与证据约定

规划者应设计最小 schema，并区分必填字段、可选字段和派生字段。至少考虑：

- workload_run_id、span_id、parent_span_id、operation_type、开始/结束时间。
- agent_id、parent_agent_id、workflow_round_id、stage_type、stage_occurrence_id、request_id、attempt_id，以及可选的 engine_iteration_id、batch_id、kernel_invocation_id；保留来源原始编号与缺失状态。
- 显式 depends_on、fork/join 关系或其他依赖来源；依赖可标记为 observed、declared 或 inferred。
- LLM 的模型、请求 ID、规范化后的输入/输出 token、可选 reasoning token、缓存读/写 token；保留 raw usage，并注明提供方、精度、是否为另一字段子集及统计口径。
- 各阶段的时间边界、elapsed/self/cumulative/critical-path 口径、采集误差和关联依据；请求级与设备级耗时分别保留。可取得时保留请求发出、服务接收、入队/准入、Prefill、首 token、Decode 与结束事件，按明确口径计算 TTFT、TPOT/ITL 和总请求延迟。
- 缓存类型、作用域、命中/查询 token 或请求量、读写量、占用、容量、单位、分母和采样区间；缺少分母时不生成命中率。
- request/tool/resource 成本明细、货币、价格来源与快照、有效时间、billed/estimated 口径、是否包含共享资源分摊。
- 工具名称、调用参数指纹、状态、重试关系、结果大小或 token；工具是否只读/幂等可声明。
- 可选内容证据：提示词块、工具结果块、前缀 token 指纹或经用户允许的内容。
- 数据来源、版本、时间单位、时钟域、缺失项、脱敏模式和采样窗口。

同一逻辑请求在客户端、Agent 和引擎日志中重复出现时，通过关联 ID 去重；真实重试是独立 attempt，不能误删其消耗。输入 token 的规范化口径应将缓存输入包含在输入总量中一次，不能再加 cached_tokens；reasoning 若已包含在输出总量中也不能再加。不同提供方原始 usage 语义不同时，由适配器显式归一化，不能直接套统一求和公式。

总体缓存命中率按同一语义下的命中量/查询量汇总，不能对每轮百分比简单平均。Prompt cache、KV 容量利用率、工具缓存和不同 endpoint 的数据不能混合成一个含义不清的“缓存利用率”。

token 和成本在请求/attempt 或独立资源收费事件层记账，向阶段与 Agent 汇总时显示包含关系；五层关联视图不重复生成费用。没有单独 token 语义的 Kernel 行可引用相关请求，并将独立 token 标为 not_applicable，不能虚构“Kernel 消耗 token”。

输入校验应覆盖重复 ID、负时长、缺失引用、循环依赖、明显矛盾的时间和版本不支持。时间单位需要显式约定。不得静默将微秒当毫秒或补齐缺失依赖。

原始 span 树不直接等同于可计算 DAG。图不完整时仍可展示观测摘要和局部关系，但必须降低结论强度，精确收益可以留空。

Prometheus 聚合计数不能直接充当某个请求的独占指标。多个请求并发共享一个 endpoint 时，全局 KV Cache 或队列变化只能作为关联证据，除非存在更精确的关联信息。

## 8. 首批诊断规则的语义

每个规则需要独立的触发条件、所需证据、反例、缺失数据行为和收益计算条件。

### R1：上下文增长与工具结果放大

报告连续 LLM 调用的输入增长、工具结果占比和重复携带量，定位到调用和内容来源。只有总 input_tokens 时，只能报告增长，不能声称具体工具导致膨胀。

不能假设输入 token 减少 30% 就使请求延迟下降 30%。有缓存、非线性 Prefill 或并行执行时尤其不能作线性换算。

### R2：重复工具调用与疑似重试循环

识别相同工具、参数、资源版本和连续失败/无进展的重复尝试。只掌握名称和参数时，输出“建议检查的重复调用”，不能直接认定可删除或缓存。

负例至少包括状态轮询、文件已被修改后的重新读取，以及必须执行的独立审查。只有幂等性、输入版本和依赖条件足够明确时，才计算移除候选调用的条件性上限。

### R3：前缀复用受损候选

在用户允许的内容或足够细粒度的指纹下，定位稳定前缀的分叉位置，例如前部时间戳、随机 ID、工具 schema 顺序变化。

字符/字节相似度不等于模型 token 前缀相同，单个整段 hash 也无法确定首个分叉位置。未取得真实 tokenizer/chat template 的结果要标记近似。

无 cache usage 或服务端证据时，只报告前缀稳定性风险。稳定前缀不代表一定应命中：还可能受缓存开关、块大小、路由、TTL、驱逐或租户隔离影响。

## 9. 关键路径与收益上限的计算边界

对可验证的固定执行依赖图 G，以活动耗时 w 计算基线完成时间 T(G,w)。对候选修改后的耗时 w' 重新求图完成时间：

```text
saved_time = T(G, w) - T(G, w')
reduction_fraction = saved_time / T(G, w)
speedup = T(G, w) / T(G, w')
```

将候选活动耗时设为零，得到的是当前图模型下消除这些活动耗时的条件性上限。更实际的加速倍数情景可以把耗时改为原来的 1/s。

必须注明：依赖关系、其他活动耗时、外部等待、资源分配和任务行为按模型保持不变。新的输出、缓存状态、调度和竞争可能使真实系统偏离该模型。

图模型应先能在声明的误差范围内解释观测到的任务时间。应用间隙、外部等待和未知耗时必须保留，不能自动压掉；无法解释的差额需要显示，必要时禁止输出精确上限。

父 span 的 elapsed time 与子 span 不能重复计费。按层报告应对可归因活动计时，并处理并行覆盖，不能把各层耗时直接相加当成 wall time。

同一条关键路径上的收益、不同层涉及相同活动的收益存在重叠。单项上限不能相加成“总收益”；组合情景必须重新计算。p95 也不能由各阶段 p95 求和，需对任务级结果重新聚合。

手算验收例：A 工具 10 秒、B 推理 15 秒同时开始，任务等待二者。基线 15 秒；A 降到 1 秒或 0 秒，任务仍为 15 秒；B 加速两倍后任务为 10 秒，节省 5 秒；B 降为 0 秒，任务仍为 10 秒。

无法取得 Prefill/Decode 分解时，可以对整个 LLM 调用作反事实分析，但不能把该上限标成缓存、调度或 Kernel 专属收益。仅有 Agent trace 时，Kernel 改善空间应标为未知。

## 10. Finding 与优化排序

每条 finding 至少包含：

- 稳定 rule_id、受影响运行/Agent/轮次/阶段实例/调用和面向用户的简短说明。
- 原始观测引用、派生计算方法、依赖的数据版本。
- evidence_level：observed、inferred、experiment_supported。
- 建议的责任层，可为多层或 unknown；不是强行归责到单一团队。
- 支持证据、反证、缺失信息，以及会推翻当前判断的条件。
- 收益目标、已观测量、可计算的条件性上限与假设；无法计算时写原因。
- 是否可能影响任务正确性，以及下一项验证建议。

首版置信度使用有解释的等级，不输出未经校准的“87% 正确概率”。实验结果也只能在其控制条件与样本范围内增强判断。

报告分开呈现“有可计算收益的候选”和“值得补充证据的未知项”。对相同目标可按上限、证据强度和覆盖范围排序，但不能将所有未知层排为低优先级。

理论收益大但证据弱的候选，应优先建议验证。没有实测或性能模型时，不编造“预计能改善 18%～26%”或开发工期。默认不生成一个掩盖假设的综合分数。

## 11. 用户体验与输出示意

以下命令是期望的产品接口，不是已经存在的命令；实施计划可在保留语义的前提下收敛参数：

```bash
agent-infertriage demo --output-dir results/demo
agent-infertriage analyze evidence/ --mode offline --output-dir results/offline
agent-infertriage analyze evidence/ --mode agent --model-config model.toml --output-dir results/agent
```

首屏报告回答：任务慢在哪里、数据能看到哪些层、每轮/每阶段用量如何变化、先检查什么、理论上限是多少，以及本次诊断自己花了多少 token 和时间。两条路径使用同一套报告结构，并显示 mode。

报告至少有四个可查看部分：workload 总览与覆盖矩阵；按 Agent/轮次/阶段展开的时间与用量明细；诊断结论及证据/收益上限；diagnosis 自身用量回执。终端必须有最终回执，JSON 必须有结构化字段，HTML 不能省略该回执。

以下仅为结构示例，数值不代表实测结果：

```text
被分析任务：workload_run_id = example-workload
数据覆盖：Agent + LLM + Tool；无服务端请求分解或 Kernel profile
轮次明细：可展开每个 Agent 的全部轮次及阶段内多次调用
用量明细：按请求显示输入/输出/缓存 token，按相同口径聚合
成本：按已知价格/账单计算；未知价格保留 unknown

候选 1：连续重复的只读文件读取
证据：call-12 / call-14，输入版本相同；可追溯至依赖图
端到端节省上限：在固定图条件下为 1.8 秒
验证：确认两个读取之间文件未改变，且不存在必要刷新语义

候选 2：输入上下文持续增长
证据：第 3～9 轮输入 token 增长；内容来源覆盖不完整
可节省时间：未知，缺少可移除内容与阶段耗时模型
下一步：检查工具结果来源，并补充 Prefill/缓存证据

调度：未知，缺少服务端证据
Kernel：未知，缺少 profile

本次诊断：diagnosis_id = example-offline，mode = offline，status = completed
诊断新增模型调用：0 次；输入/输出/总 token：0 / 0 / 0
诊断总耗时：0.42 秒；新增模型/API 费用：0；本地计算资源费用：未计价
上述诊断用量与原任务用量分别记录
```

报告同时提供可展开的时间轴/依赖关系与证据引用。HTML 自包含，不依赖账号、外链脚本或后端；输入内容按文本转义展示，避免工具输出被当作可执行 HTML。

Agent 模式同样在最终回执中显示累计用量，例如 4 次模型调用、3,200 输入 token、800 输出 token、合计 4,000 token、7.8 秒诊断 wall time，并附逐轮模型/工具调用记录。该示例是假设所有 usage 均已取得的展示样例；缺失 usage 时必须显示已知小计和覆盖率，不能把小计写成完整总量。

README 优先提供英语，并附中文说明。用户应能从仓库样例快速得到首份报告，而不用先安装推理引擎。

## 12. 默认行为、内容与费用

默认使用 offline 模式：离线分析不发起网络请求、不调用 LLM、不发送 telemetry。用户显式选择 agent 模式时，才可以调用其配置的模型服务；这不包含主动探针授权。安装依赖和用户显式选择的数据导入不与“离线分析”混为一谈。

没有正文也应能分析时间与结构。内容级规则需要可选的本地正文或明确声明能力的指纹数据；缺少内容时停用相应检查并解释原因。不能同时声称“从不访问内容”和“准确指出提示词哪个字段破坏缓存”。

被分析任务、诊断 Agent 分析和主动探针的预算分别管理。token 数是估计时需说明误差；以请求数、最大输入/输出长度、并发和总时长形成实际停止边界。未取得价格不能声称精确美元预算。

产品命令不应在常规分析过程中要求用户调整配置或授予自动修改权限。显式实验只允许列明的请求，达到预算后返回已有证据与未完成状态，不继续扩大扫描。

### 12.1 被分析任务的 token、缓存和成本

workload 至少报告输入、输出、总 token，以及在可获得时报告缓存读/写和 reasoning token。每项保留 reported/estimated/unknown 状态。阶段和轮次分解必须能回溯到原始请求，汇总去重后能与任务总量核对；未归属部分单独列出。

缓存利用率要注明缓存类型、单位和分母，同时显示可用的命中 token/请求数、查询量与 KV 占用等原始值。不能把 Prompt Cache 的计费折扣等同于 KV 显存节省。

成本至少支持用户提供的价格快照或明确的账单证据，区分模型输入/输出/缓存读写、工具/API，以及可选的自建 GPU 资源费用。价格应带货币、版本或有效时间；没有价格不能推导成本为零。known_cost_subtotal 与无法计价的部分分别保留，费用总量不完整时显示 coverage/unknown。

自建推理可以显示按 GPU 时间/租用费等口径估算的成本，但共享 GPU、批次和并发请求的分摊必须注明方法。不能同时将同一 GPU 的推理资源成本与其内部 Kernel 成本相加，也不能不加说明地将按 token 和按资源估算的同一服务费用相加。

### 12.2 本次诊断自身的 token 与时间回执

每次运行创建独立 diagnosis_id，关联目标 workload_run_id。两条路径在成功、可恢复错误、预算耗尽和可捕获的取消时都必须生成最终或部分回执。进程被强制终止时依赖已落盘事件恢复，并明确标记 incomplete，不能承诺未返回 usage 的调用具有精确总量。

回执的最小字段：

- mode、status、started_at、ended_at、wall_time_ms、measurement_scope。
- analysis_round_count、model_call_count、tool_call_count，以及重试/失败调用计数。
- input_tokens、output_tokens、total_tokens、可选 cache_read/cache_write/reasoning token，以及各字段口径。
- usage_source、usage_completeness、known_token_subtotal、unknown_usage_call_count，必要时区分模型上报与本地估计。
- model_cost、tool_api_cost、probe_cost、known_cost_subtotal、unpriced_items、currency 和价格来源；本地 CPU/GPU 费用如未估算则注明未计价。
- 每次分析轮、模型请求、工具调用和探针的时间与用量引用；LLM 的最终总结调用也包含在内。

usage 以提供方返回为优先，保留原始数据；缺失时可给明确标注的估计。只要有未能计数的请求，精确 total_tokens 就应为空或明确标为不完整，并展示已知小计。不能因请求失败、流式中断或 usage 未返回而记为零消耗。

diagnosis 的总 token 统计涵盖分析模型、最终总结、重试、显式启用的模型工具/子 Agent，以及主动探针向模型发出的请求。按 analysis、probe 等用途分开小计，再按模型请求事件去重汇总；诊断 Agent 是在分析探针结果，不能把同一探针 usage 同时记为两次。原任务历史 token 不计入新增诊断消耗。

offline 模式在没有任何模型调用时应明确报告新增模型 input/output/total token = 0，不能由于原日志含大量 token 而报告为诊断消耗。agent 模式即使模型运行在本地，也应记录实际模型用量；新增计费可以为零，但不能省略 token 与耗时。

wall_time_ms 使用本地单调时钟计量，从诊断命令/运行开始，覆盖读取、解析、确定性计算、Agent 模型等待与工具执行、可选探针及报告主体生成，直到最终用量回执快照。measurement_scope 写明最终回执的末次序列化/终端刷新不含在快照内。模型累计服务时间、工具累计时间和总 wall time 分别报告；并行耗时不能简单求和当总耗时。

所有模型调用结束并记录最终 usage 后，才冻结用量快照；回执由确定性程序生成，不再调用模型润色，以免漏记最后一次调用。终端、JSON 与 HTML 中的诊断回执必须引用同一快照。运行事件增量保存，异常时可以输出已知开销与未完成原因。

## 13. 实现原则与规划默认项

- 优先 Python CLI，采用 uv 管理开发环境；已有仓库约束优先。
- 核心数据模型、输入适配、依赖图/反事实计算、规则、Agent 分析执行器、用量账本和报告渲染分离。
- 使用版本化 schema、稳定 finding ID 和确定性输出，便于自动测试和社区贡献。
- 首版规则可由 Python 实现；不提前建设通用规则 DSL、插件市场或复杂数据库。
- HTML 使用轻量模板和嵌入资源，不为首版引入前后端分离部署。
- 离线样例和自动测试必须可在无 GPU、无 API key 环境运行。Agent 循环与记账用可控的 mock 响应验证；真实模型适配器和引擎集成检查独立且显式启用，并分别报告验证状态。
- 项目按 Apache-2.0 作为许可证默认候选，依赖及示例素材需兼容。外部 trace 不能直接拿未经授权的数据分发。

## 14. 验收案例与成功标准

阶段 A 必须以预先写明答案的案例验证，不能只用自动生成的报告自证正确。

| 案例 | 应得到的结果 |
| --- | --- |
| 两个顺序活动分别为 10 秒、15 秒 | 基线 25 秒，消除前者的条件性上限为 10 秒 |
| 并行活动 A=10 秒、B=15 秒后汇合 | 消除 A 节省 0 秒；B 加速两倍节省 5 秒 |
| 父 span 20 秒，内部子活动共覆盖 20 秒 | 不报告为 40 秒 |
| 两条等长关键分支 | 只缩短其中一条不错误宣称整体改善 |
| 显式外部等待与缺失时间 | 保留等待/未归因时间，不能自动视为可消除开销 |
| 依赖缺失或跨时钟未对齐 | 输出覆盖限制，无法支持的精确上限为空 |
| 只有总输入 token，输入逐轮增长 | 可报告增长，不归因到某个具体工具结果 |
| 同一文件版本被重复只读读取 | 标记重复候选并说明可移除条件 |
| 文件变更后重读、轮询、独立审查 | 不直接判定为无用调用 |
| 内容前部存在动态字段，但没有 cache usage | 报告缓存风险，不能声称已证实缓存失效 |
| 重复前缀已命中缓存 | 不把重复 token 全部算为未缓存开销或全价浪费 |
| 只接入托管 API trace | 调度与 Kernel 为未知，不给确定性后端诊断 |
| 多条建议影响同一活动 | 不把单项收益相加 |
| 工具结果含 HTML/脚本字符串 | 报告显示转义文本，不执行内容 |
| 同一阶段在 3 个工作流轮次内各有 2 次调用 | 六次调用明细均保留，可按阶段、轮次和调用展开 |
| 一轮调度关联多次 Decode/Kernel 调用 | 不把模型 step、workflow round 和 retry 编号混为同一维度 |
| 完整五层证据包含时间、用量、缓存及成本 | 五层均展示，跨层引用同一请求时 token/成本只汇总一次 |
| 缺少 Kernel profile 或只记录全局 GPU 利用率 | Kernel 耗时/成本归因为 unknown，而不是 0 或伪估计 |
| 缓存命中率为 1/1 和 0/9 两轮 | 相同语义下总命中率为 1/10，不是 50% |
| 规范化输入 1,000 token，其中缓存读取 800；输出 100，其中 reasoning 60 | 总 token 为 1,100，不重复加缓存与 reasoning 子集 |
| 原任务日志记录 100,000 token，offline 分析未调用模型 | workload 保留历史用量；diagnosis 新增 token 为 0，实际诊断时间被记录 |
| Agent 两轮模型调用，最终总结又调用一次模型 | 三次调用的输入/输出/缓存、时间与费用全部纳入本次 diagnosis |
| Agent 模型调用失败或流式中断且无 usage | 显示未知调用、已知小计和不完整状态，不把未知消耗算为 0 |
| 同一请求同时出现在 Agent、代理和引擎日志 | 合并其证据并去重用量；真实 retry 作为独立 attempt 计量 |
| agent 模式未额外启用主动探针 | 可分析日志和调用配置的分析模型，但向被分析服务发送的测试请求为 0 |
| 诊断执行中预算耗尽或发生可捕获异常 | 输出 partial/failed 回执，保留已发生的模型用量与耗时 |
| 多个诊断模型调用并行 | 总 wall time 按时钟计算，不直接取各调用时长之和 |
| 缺少价格或部分请求无价格 | 成本总量标为不完整，保留已知费用及未计价项目 |
| 比较终端、JSON 与 HTML 的 diagnosis 字段 | 使用同一最终快照，包含最终模型总结用量 |

阶段 A 的交付还应满足：

1. 一个命令生成可离线查看的示例报告，并导出对应 JSON；全阶段/逐轮维度和数据覆盖状态可见。
2. 至少一个实际可用且注明支持范围的真实 trace 导入路径。
3. 原始观测、依赖和收益计算可追溯，报告明确区分观测、推断与未知。
4. 三类规则均有阳性、阴性和证据不足案例。
5. 默认 offline 分析可在禁用网络环境下运行，不消耗推理 token，同时输出实际诊断耗时与 0 token 回执。
6. 相同输入与配置下，offline 的数值和 finding 一致；agent 可以产生不同的文字解释，但同一证据对应的确定性计量必须一致，测试不依赖未固定的模型输出。
7. agent 模式能使用真实模型适配器完成至少一轮日志读取—分析工具调用—结论生成，并输出本次完整/部分 token 与时间回执；其可控流程和记账有 mock 测试。
8. workload 的逐阶段/逐轮时间、token、缓存、成本能按来源口径核对；unknown/not_applicable 不被计作零。diagnosis 与 workload 总量不混合。

阶段 B 另行验收：指标语义与来源版本有测试；服务共享时不过度归因；探针没有显式启用时发出请求数为零；启用后遵守请求/长度/时间预算，允许缓存、排队或网络因素仍无法区分的结果。

真实案例用于展示可解释性与实用性，不凭单个案例宣称适用于全部 Agent。后续需要积累匿名且经允许的事故样例与有对照的实验数据。

## 15. 主要风险与应对方向

最大的风险是 trace 不足以恢复依赖关系，导致“关键路径”只是一个看起来可信的图。应先定义数据能力等级和严格降级路径。

第二个风险是通过 token、TTFT 或全局 GPU 指标过度推断内部病因。应限制规则所能声称的证据层，并在缺失时保留未知。

第三个风险是把理论上限当成现实预测，或者把省钱、降低负载和缩短任务时间混成一个收益。报告要分别命名，并保留所有计算条件。

第四个风险是首版范围扩张。首版冻结为共享确定性分析核心、offline/agent 两条路径、逐轮全阶段视图与诊断开销回执；后续再补在线服务端采集和主动探针。先用标准证据包接纳 Kernel 标注，不在首版开发新的 GPU profiler。

第五个风险是诊断 Agent 自己成为不可见开销。必须统一记录所有分析轮、模型/工具调用、重试和最终总结，并在两条路径结束时输出回执；缺失 usage、未知价格与并行时间不能被隐藏。

## 16. 配套实施计划需要明确的内容

请依据本草案和目标仓库实际状态形成独立 plan.md。至少明确：

1. 阶段 A 的冻结范围、完成条件与阶段 B 的后续边界；首版必须交付 offline 与 agent 两条路径及诊断开销回执。
2. 输入 schema、依赖信息的来源、能力等级、五层全阶段/多轮关联与降级语义。
3. 能解释观测时间的图模型，以及关键路径和反事实收益算法。
4. 三类规则各自所需证据、误报反例和收益计算条件。
5. 选择首个真实导入来源的依据，缺失字段如何处理。
6. 每个实现任务对应的可检验产物和验收案例。
7. 终端/JSON/HTML 的最小输出，以及没有服务端数据时的报告行为；两条路径复用相同结果和计量格式。
8. Agent 模型适配、只读工具、分析轮次、预算与失败停止机制；日后接入指标和主动探针需要保留的最小接口。
9. workload 的耗时/token/缓存/成本归一化和去重，以及 diagnosis 自身的独立用量账本、最终快照、时间测量范围和异常回执。

实施者可直接确定常规技术选择并写出理由，不需要把所有实现细节留成 PENDING。只有会改变产品边界或依赖无法取得的数据/权限的事项才需要列为真实阻塞。

设计和代码审查应重点检查：依赖是否真实、耗时是否重复计算、上限是否写明条件、未知是否被错误填零、缓存机会是否被当成实际命中、单阶段多轮是否丢失、各层 token/成本是否重复累计、诊断模型最终调用是否漏计，以及首版是否被扩成通用平台。不能将 Agent 分析路径推迟到后续阶段，也不能把它与主动探针合并成一个隐式收费开关。

本次工作只细化实施计划，不自动开始编码、模型实验或部署。
